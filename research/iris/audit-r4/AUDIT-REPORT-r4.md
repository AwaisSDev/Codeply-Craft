## 2. The "42 / 12 / 28" vs "144 / 24 / 0" discrepancy: exact cause

Both are correct; they count different things.

* **144 / 24 / 0** is the manifest the Kaggle job built at run time. The job's dataset deliberately omits
  `data/raw/test` (`scripts/kaggle/run.py`: "the test split is not uploaded"), so the build writes test = 0.
  Train 144 = 60 template-drill episodes (`syn01`) + 42 Opus-authored (`tr01-03`) + 42 Sonnet-authored (`tr04-06`);
  val 24 = `va01` (Opus) + `va02` (Sonnet). Reproduced exactly: building `data/raw` without the test folder gives
  144 / 24 / 0 with the same hashes and the same log line `train-test: 0 shared entities` (the full repo build
  says 2).
* **42 / 12 / 28** counts the **Opus-authored teacher episodes only**: train `tr01-03` = 42, val `va01` = 12,
  test `te01`+`te02` = 28. It leaves out the drills and the later Sonnet shards. No document in this repository
  states these figures, so I could not find the report they came from. **Where did you see them?** The
  breakdown above is the only one consistent with the shard files.
* The full repo manifest is **144 / 24 / 28** (1,258 / 184 / 203 examples). Name collision to avoid:
  `results/val/iris-r1`, `iris-r2` are old CPU runs of Qwen3-0.6B on the old 12-episode val. They are not the GPU
  r2 / r3.

## 3. Leakage

* No exact-duplicate messages or near-duplicate sessions across splits. Test 6-gram overlap with train: mean
  0.18 %, max 6.9 %.
* **Missed by the build check:** the invented names "Ledgerline" (train `tr03-e12`, val `va01-e01`) and "Project
  Kestrel" (train `tr06-e09`, val `va02-e04`) appear in two splits. The template boilerplate emails and the "NOTE TO
  AI ASSISTANT" injection message are reused across splits (30 train / 9 val / 1 test messages), so injection
  resistance is barely measurable. Impact on reported F1 is small (2 of 24 val episodes). `va01-e01` should be
  excluded in a sensitivity analysis, and new data must use unique injection texts.
* Model selection used val loss on 120 val examples at up to 10 checkpoints. That is mild optimism on val. Test is
  untouched.

## 5. Diagnosis: why r3 has 0.42 open-loop F1 but 0.33 closed-loop

### 5.1 Per operation (1.7B r3, open loop; closed loop in brackets)

| Op | Result |
|---|---|
| add | recall 0.35 [0.30]; precision 0.38 (172 of 177 false memories are adds) |
| update | right op + target 34 / 57 = 0.60 [12 / 20]; precision 0.76 when used |
| confirm | 3 / 14 = 0.21 [1 / 4]; misses become duplicate adds or updates |
| retract | recall 8 / 17 = 0.47 [2 / 5]; **precision 0.32 [0.11]** |
| conflict | **untestable: 0 gold examples in train and val** (2 in test) |
| skip | 71 / 100 recorded, right reason 96 %; only 7 % of labelled skips stored as memories |

### 5.2 The open/closed gap is half metric, half real

The strict closed loop links a model-written memory to a teacher fact only when entity and value strictly match.
A memory that states the right fact in other words stays "unlinked". Every later update, confirm or retract of that
fact is then re-derived as an `add`, and the model is penalised again in each session. Store links are evaluation
bookkeeping only (they are stripped from the prompt), so the cached generations can be re-scored offline
(`closed_gap.py`):

| 1.7B | Open F1 | Closed, strict | Closed, evidence-linked | Gap closed by linking |
|---|---|---|---|---|
| r2 | 0.404 | 0.311 | 0.355 | 47 % |
| r3 | 0.420 | 0.333 | 0.371 | 44 % |

* With evidence linking, r3's closed F1 by session is flat (0.40, 0.35, 0.35, 0.36, 0.38) instead of falling
  (0.40 to 0.25). There is no runaway compounding.
* The **real** residual gap (about 0.05) is mainly **acting on its own memories**. Once linked, val has 42 gold
  updates on model-written rows and r3 gets 50 % of them (often a fresh `add`). Retraction precision falls to 0.11.
* Strict F1 stays the primary metric (pre-registered); the evidence-linked score becomes a secondary diagnostic.

### 5.3 Where the errors are (open loop, 1.7B r3)

| Error | Share | Comment |
|---|---|---|
| False memory on a statement the teacher labelled, but different value / entity | 91 of 177 false (51 %) | granularity and naming ("owns the transfers service" vs "backend engineer"), some real errors (dropped or wrong dates) |
| False memory on a statement the teacher did not label | 70 (40 %) | sampling: ~25-30 % plausible teacher omissions, the rest trivial or invented; the guard checks that the quote exists, not that it supports the value |
| Other speaker's statement attributed to the user | 9 (5 %) | |
| Stored a joke / hypothetical / hearsay / secret / injection | 7 (4 %) | **skip traps are not a main cause** |
| Missed gold facts | 213 of 359 (59 %) | 107 statements untouched; implied facts recall ~23 % vs stated ~43 %; tasks and plain facts ~32 % vs events 65 % |
| Schema-dropped ops (bad ref / type / kind) | ~10 % of sessions | r3 28 vs r2 15 per 240 outputs; removable by constrained decoding |

### 5.4 Slices (val too small to rank most of these)

* **Source:** calendar easy (F1 0.79 open); screen 0.32 open / 0.12 closed (13 gold ops); email 0.42 / 0.26;
  personal and work chat ~0.35.
* **Language:** English 0.42, mixed 0.53, Roman Urdu and Urdu 10 sessions each (not rankable). Roman Urdu empty
  sessions are mishandled (empty-session accuracy 0.71 vs 1.0 English).
* **Topic boundaries:** 85 of 120 open-loop sessions show memories from other conversations; r3 acted on one in 3
  of 76 update / retract / confirm ops (r2: 0). Not a main cause.
* **Label source:** r3 open F1 is 0.36 on `va01` (Opus-labelled) vs 0.48 on `va02` (Sonnet-labelled). Author and
  labeller are confounded, but this fits the review result that Opus labels are noisier (Section 6).

### 5.5 Training dynamics

* 1.7B r2: train loss 0.04-0.06 by the end, val loss flat from step 300 (≈ epoch 1.9, 0.2152) to 471
  (0.2140). Memorisation, little gain after ~2 epochs.
* r3 val loss is best at step 100 (0.2123), then rises to 0.2335. The evaluated r3 is r2 plus ~100 steps.
  **r3 minus r2 is not significant** (paired bootstrap, open F1 [-0.020, +0.053], closed [-0.029, +0.078]).
  r3 should not be continued.
* The r3 self-output data was built from a model that had seen those episodes, but its stores were not cleaner
  than val's (53 % unlinked rows vs 63 %). Its targets have the same linking flaw as the metric: a fact the model
  stored in other words is re-labelled `add`. This affected few targets (7 of 840 adds have an obvious paraphrase
  row), but the data never teaches "update your own memory", which is the real closed-loop weakness.

## 6. Label quality is a ceiling

Blind reviews use the same strict match as IrisBench, so annotator-teacher agreement bounds strict F1. Agreement:
Sonnet-authored shards 0.92-0.98 (0-1 of 40 sessions with an error); **Opus-authored train shards 0.805 (7 of 40
sessions with an error)**. These shards are 286 of 904 train observe examples. **Test (`te01`, `te02`) is
Opus-authored and was never reviewed**, so its strict ceiling may be near 0.8 and its noise will blur r4-vs-r3
differences.

## 7. Highest-impact causes, ranked

1. **Low add precision and value granularity** (51 % + 40 % of false memories). The model finds the right statement
   about 65 % of the time but phrases the slot or value unlike the labels, or stores trivia. Fix: consistent labels
   (repair the Opus shards, explicit value and storage-threshold conventions) and contrastive "do not store"
   negatives drawn from ordinary statements, not more joke / hypothetical traps.
2. **Recall of implied facts, tasks and other people's facts.**
3. **Acting on its own memories** (update / retract / confirm on model-written rows): the real closed-loop gap.
   Nothing in training shows the model its own paraphrased rows with the correct `update` target.
4. **Training recipe:** memorisation after ~2 epochs, one seed, a drill share (35 %) that I11 showed does not
   transfer, and continued training (r3) that adds nothing measurable.
5. **Measurement:** val of 24 episodes (closed F1 95 % CI ±0.057), no conflict examples anywhere, unreviewed
   test labels, unknown seed variance.

More of the same data is not the fix. Items 1 and 3 need different targets, not more episodes.
