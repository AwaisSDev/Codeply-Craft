# Iris foundation study: failures first, then models (2026-11-19)

**Question.** Which small model can reliably understand a person's context, tell facts from noise, and keep an
accurate memory over time with the fewest false memories?

**Scope of this document.** Analysis and plan only. No model was trained or prompted, and no test file was read.
Every number is either regenerated by a committed script in this folder (tag **[M]**, measured from committed
artifacts or primary sources today) or labelled an **estimate**. Vendor benchmark numbers are context, not evidence
about Iris. All model numbers are on **validation** (24 episodes, 120 sessions, one training seed).

## 1. Where Iris fails, and who is to blame

### 1.1 The controlled comparison we already have

Qwen3-0.6B and Qwen3-1.7B were fine-tuned in the same Kaggle run (I16) with the same data, recipe, seed, decoding and
evaluation. A failure that shrinks from 0.6B to 1.7B is **capacity-sensitive**, so a stronger foundation can help.
A failure that stays flat or grows is **bound to something both share**: labels, data, prompt, contract or metric.
This is the best evidence available on "base model versus everything else" without running anything new.

Headline numbers (strict IrisBench match, val; reproduced exactly from the committed details files) [M]:

| Run | Open P / R / F1 | Closed P / R / F1 | Wrong-fact share open / closed | **False memories per 100 sessions** open / closed | End-state F1 |
|---|---|---|---|---|---|
| rules (re-run today) | 0.33 / 0.006 / 0.011 | 0.33 / 0.005 / 0.011 | 0.67 / 0.67 | 1.7 / 1.7 (6 predictions in 120 sessions) | — |
| 0.6B r2 | 0.37 / 0.27 / 0.31 | 0.33 / 0.25 / 0.28 | 0.59 / 0.66 | 132 / 157 | 0.25 |
| 1.7B r2 | 0.43 / 0.38 / 0.40 | 0.35 / 0.28 / 0.31 | 0.54 / 0.63 | **141 / 156** | 0.30 |
| 0.6B r3 | 0.36 / 0.28 / 0.31 | 0.28 / 0.21 / 0.24 | 0.61 / 0.69 | 143 / 161 | 0.20 |
| 1.7B r3 | 0.43 / 0.41 / 0.42 | 0.34 / 0.33 / 0.33 | 0.53 / 0.63 | **148 / 183** | 0.30 |

**The most important finding: going from 0.6B to 1.7B did not reduce false memories.** The wrong-fact *share* fell
(0.59 to 0.54) only because the larger model also found more true facts. The number of false memories a user would
live with rose slightly in open loop (132 to 141 per 100 sessions) and was flat in closed loop (157 to 156). The
self-output round (r3) added more false memories, not fewer (1.7B closed: 156 to 183).

Label noise is a ceiling, and it binds harder as the model improves. F1 on Opus-labelled `va01` vs Sonnet-labelled
`va02` is 0.26 vs 0.36 (0.6B r2) and 0.33 vs 0.48 (1.7B r2): the gap grows from 0.10 to 0.15 with capacity.

**Conclusion of §1.** Most of Iris's false memories (85 % at 1.7B) come from what the model is taught to store and
how it is scored, not from what the base model can read. A foundation change can fix Urdu-script reading, dates,
value phrasing, quote fidelity and update targeting. Those are real but secondary. The r4 data work (storage
threshold, label repair, own-memory updates) is still the main lever, and it is foundation-agnostic. **Choose the
foundation for Urdu, cost, tooling and abstention quality, and do not expect it alone to cut false memories.**

### 1.4 Verified baselines and their limits

* **Zero-shot Qwen3-0.6B, F1 0.02: verified, but not comparable.** Re-scoring the cached generations against the val
  build they were run on (commit `60129998`, val sha256 `cf92649d…`, 12 episodes / 60 sessions, va01 only) gives
  F1 **0.021**, P 0.167, R 0.011. The reported false-memory share (0.917) predates the I11 metric fix; current code
  gives 0.75. Q8_0 GGUF, llama.cpp, schema-constrained, p50 12.6 s per session on this CPU. It is **not comparable**
  with the 24-episode val of r2/r3 and must be re-run.
  Diagnostic: stripping the leading speaker label from quotes raises F1 to 0.069 (precision 0.16). The format
  failure is the prompt's. The rest is the 0.6B model.
* **Zero-shot Qwen3-1.7B: never run.** It is in the plan.
* **Rules, F1 0.011 (I16): verified today** on the current val, open and closed loop. It made 6 predictions in 120
  sessions. It is a cost reference, not a precision reference.
* **r2 / r3:** committed val results are byte-identical to the Kaggle output (audit r4). They come from HF fp16 on a T4,
  unbatched and unconstrained, so they are a different backend from the GGUF zero-shot runs. The adapters live in the
  private Kaggle dataset `codeply-iris-adapters-v1` and are not reachable from this container.

## 4. Deployment view (what parameter count hides)

* **KV cache differs by an order of magnitude at equal size.** Hybrid models keep a growing cache in only a few
  layers: Qwen3.5-2B 24 MiB and LFM3 27 MiB at 2K tokens, against 224 MiB for Qwen3-1.7B and 288 MiB for Qwen3-4B.
  Iris prompts are ≤ 2K tokens today, so this matters for phones and long batches, not for the current benchmark.
* **Urdu script cost depends on the tokenizer, not the size:** 1.88 (Gemma 4) to 3.83 (Granite) tokens per word.
  Roman Urdu is ~1.8-2.0 for every model. Urdu is ~8 % of val sessions, so mean prompt tokens differ by only ±5 %
  across models. For an Urdu-script user, Qwen3 reads ~65 % more tokens than Gemma 4.
* **Files:** Gemma 4 E2B is 3.12 GiB at Q4 (per-layer embeddings are lookups: large on disk, cheap per token), against
  1.19 GiB for Qwen3.5-2B and 1.02 GiB for LFM3.
* **Measured anchors on this container (4 vCPU Xeon, AVX-512/AMX):** Qwen3-4B-Instruct-2507 Q4_K_M 78 tok/s prompt,
  6.8 tok/s generation (llama-bench, 2026-11-04); zero-shot Qwen3-0.6B Q8_0 mean 15.8 s per session (1,200 prompt +
  274 generated tokens); fine-tuned 0.6B Q8_0 mean 4.6 s (512 + 94); production LFM3-1.7B p50 5-12 s, p95 18-28 s.
  Every other latency figure in EVAL-PLAN.md is an **estimate** scaled from these, to be replaced by llama-bench in
  stage 0. The CPU speed of the `qwen35` and `gemma4` kernels in particular is unmeasured.
* **Fine-tuning on Kaggle T4 (fp16 only, no bf16):** Qwen3 sizes work (done). Qwen3.5 needs the Gated-DeltaNet CUDA
  kernels (flash-linear-attention, causal-conv1d) on sm75. **Unverified**; without them it falls back to reference
  kernels (2x slower on CPU in I2). Gemma 4 E2B holds 5.1B weights (≈10 GB fp16), and Gemma families have a history
  of fp16 activation overflow. On a T4 that is a real risk: plan QLoRA and a bf16 GPU if one is available. Qwen3-4B
  fits with gradient checkpointing or QLoRA.
* **Phones:** Qwen3.5-0.8B / 2B (0.5 / 1.2 GiB, tiny KV), LFM3-1.7B (vendor phone numbers, licence-capped) and Gemma 4
  E2B (designed for phones, large file) are the realistic tier. 3-4B dense models are not.

## 6. Answers

1. **The 3 models to test first:** Qwen3.5-2B, Gemma 4 E2B, Qwen3-4B-Instruct-2507, run against zero-shot Qwen3-0.6B
   and Qwen3-1.7B under one prompt and backend. Between them they cover the three questions that matter: same-family
   newer architecture at the same cost, best multilingual tokenizer, and pure capacity.
2. **Strongest candidate for future fine-tuning: Qwen3.5-2B, provisionally.** It changes the least that works
   (data, contract, trainer and r4 plan carry over), costs about what 1.7B costs, reads Urdu with fewer tokens, and
   has an Apache licence. Two conditions before it can replace 1.7B: its DeltaNet kernels must train on the available
   GPU (stage-0 smoke test), and it must beat Qwen3-1.7B in a **matched LoRA pilot** on the r4 data. Zero-shot
   ranking alone does not decide this (§7 of the plan).
3. **Keep Qwen3-1.7B as the current lead: yes.** It is the only model with fine-tuned Iris evidence, and the r4 work
   that targets the dominant failures does not depend on the foundation. Change the lead only when a challenger
   beats it in the matched pilot: closed-loop F1 up, and false memories per 100 sessions down, with the paired
   bootstrap interval excluding zero.
4. **Qwen3.5-2B is worth the extra compute: yes, it is nearly free** (estimated within ~15 % of 1.7B per batch, and a
   10x smaller KV cache). **Qwen3.5-4B is not, as a default:** about 2x the latency on a 4-thread CPU (estimate: ~37 s per
   fine-tuned batch against ~17 s), and our own scale evidence says capacity did not reduce false memories. Run it as
   a ceiling only, and adopt it only if it cuts false memories per 100 sessions beyond the interval.
5. **LFM3-1.7B: as a reference only.** It breaks the licence requirement in FOUNDATION.md (commercial use only below
   $10M revenue), Urdu is not on its card, and its card says thinking-off is inconsistent. It stays in wave B because
   it is production's model, and IrisBench should show what Iris must beat.
6. **Most likely to reduce false memories:** no candidate has evidence of that, and our controlled scale comparison
   says capacity alone does not. On reasoning, **Qwen3.5-4B** is the most likely: it has the most capacity for the
   capacity-sensitive categories (dates, granularity, Urdu) and the broadest language coverage. Per unit of always-on
   cost, **Gemma 4 E2B** is the most likely for Urdu-script users. The plan tests this directly with false memories per
   100 sessions, precision at matched coverage (risk-coverage from token log-probabilities, so a silent model cannot
   win), and the wrong-entity / unlabelled-statement categories. Better-looking JSON is scored separately (validity,
   schema drops) and does not count towards this.
7. **Zero-shot plan with compute:** `EVAL-PLAN.md`. Wave A is ~10 CPU-hours on this container, or ~1.5-2 Kaggle T4
   hours (estimates). Waves A + B are ~23 CPU-hours. Stage 0 (backend fix, llama-bench, parity check) is ~1-2 hours and
   needs no approval of spend.

## 7. What this study cannot tell you yet

* Zero-shot scores at this size are near zero (0.02). Zero-shot screens format compliance, quoting, calibration and
  Urdu reading. It does not predict fine-tuned rank reliably. The decision needs the matched LoRA pilot (not started:
  "do not train anything yet").
* Every slice except English is tiny (Urdu script: 2 val episodes). Language conclusions are directional.
* Val has no `conflict` gold, reused injection templates, and two shared invented names (audit r4 §3). The test labels
  are unreviewed (r4 proposal D1, still open). This study does not touch test.
* One training seed everywhere. The 0.6B vs 1.7B comparison has no seed replicate.
